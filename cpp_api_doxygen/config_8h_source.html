60// ================= Dual USB-CDC transport (OpenRB-150) =================
61// Splits the single native USB CDC into TWO ACM interfaces on one cable so
62// host commands and telemetry no longer share one channel (head-of-line
63// blocking fix at the device side):
64// CMD_SERIAL -> host COMMAND input (primary CDC, USB interface 0 / MI_00)
65// TELEM_SERIAL -> replies + telemetry (second CDC, USB interface 2 / MI_02)
66//
67// The second CDC is a plain second instance of the core's PluggableUSB
68// `Serial_` class (defined in the .ino). The core already advertises the
69// IAD composite device class (0xEF/0x02/0x01) and each CDC emits its own IAD,
70// so Windows binds BOTH interfaces to usbser.sys as two COM ports with no
71// custom .inf. Endpoint budget: EP0 (control) + 3 (CDC1) + 3 (CDC2) = 7 =
72// the core's USB_ENDPOINTS cap, so exactly two CDCs fit (no room for a 3rd
73// USB function).
74//
75// Enabled by default on OpenRB-150. Define SINGLE_CDC before building to
76// force legacy one-port behavior (bench debugging over a single COM port).
77// The Bluetooth COMMAND_SERIAL (Serial3 / HC-05) path is unchanged either way.
78#if defined(ARDUINO_OpenRB) && !defined(SINGLE_CDC)
79 #define DUAL_CDC 1
80#endif

434// ---- Per-joint gesture travel ----------------------------------------------
435// Each value is a fraction of that joint's TRAVEL -- the signed distance from
436// home to the flexion end of its calibrated window:
437//
438// target = home + fraction * gesture_span(motor)
439//
440// gesture_span() is resolved per motor by NMLHandExo::getGestureSpan() from
441// home and [limit_min, limit_max], so 0.0 sits exactly at home and 1.0 sits
442// exactly ON the flexion endstop. Nothing in between ever clamps, and the
443// mapping is invertible -- which is what makes `get_gesture_angle` able to
444// report the same 0-100 number back.
445//
446// This is NOT a fraction of the window WIDTH (limit_max - limit_min), which is
447// what these constants used to mean. The old form silently assumed home sat at
448// one edge of the window; when it did not, every state clamped to the same
449// boundary and the joint had zero visible travel while still acking OK. The
450// wrist and wrist2 axes are exactly where that assumption broke.
451//
452// The thumb gets three independent knobs per state because its joints do NOT
453// share a flip direction (DEFAULT_FLIPS has thumbrot true, thumbadd/thumbflex
454// false), so a single shared value drives them physically opposite ways.
455//
456// Every joint gets THREE knobs, one per gesture state:
457//
458// EXTEND_* -> the extension posture, and the 0% end of the percent axis
459// REST_* -> intermediate posture
460// FLEX_* -> the flexion posture, and the 100% end of the percent axis
461//
462// EXTEND_* and FLEX_* do double duty: they are the two states, AND they are the
463// endpoints `set_gesture_angle` interpolates between. So
464//
465// set_gesture_angle:<g>:0 == set_gesture:<g>:extend
466// set_gesture_angle:<g>:100 == set_gesture:<g>:flex
467// set_gesture_angle:<g>:50 == halfway between the two postures
468//
469// and `get_gesture_angle` inverts it. Retuning EXTEND_*/FLEX_* therefore moves
470// the percent axis with them -- which is the point: a host's percentages stay
471// meaningful across a retune instead of pointing at raw travel that no longer
472// corresponds to a posture. REST_* is NOT an endpoint; it just lands wherever
473// its value falls on that axis (`get_gesture_angle` will report where).
474//
475// EXTEND_* need not be 0.0. It was pinned there while the axis ran from home,
476// because home IS the extension endstop as calibration defines it (the median
477// of the EXTENSION samples, see CalibrationDialog._save_profile) and anything
478// below clamped. Now that 0% follows EXTEND_* rather than home, a non-zero
479// value is a first-class extension posture that sits slightly off the endstop.
480// A hand at home then reads BELOW 0% -- `get_gesture_angle` reports 101 for it,
481// which is correct, not a fault.
482//
483// If a joint moves the WRONG WAY, negate its constants here (or fix that
484// motor's DEFAULT_FLIPS entry, which affects every gesture). If a joint moves
485// TOO FAR, shrink the magnitude. Keep EXTEND_* != FLEX_*, or that joint has no
486// axis to interpolate along and stops reporting a position.
487//
488// NOTE: a joint whose calibrated window has (almost) no room on either side of
489// home has ZERO travel no matter what is set here. Run `check_limits`, which
490// prints the resolved span per motor, to find those before tuning.
491

590// ---- Combined-motor current budget -----------------------------------------
591// MOTOR_CURRENT_LIMIT and DEFAULT_GOAL_CURRENT_MA above are PER-MOTOR knobs.
592// Neither bounds what the fleet draws together, which is the quantity the power
593// supply actually cares about: a posture that commands every joint at once --
594// `grasp:open` drives all of them to home, which calibration places AT the
595// extension endstop -- can leave many motors stalled and each drawing its full
596// goal current, browning out the board.
597//
598// The budget below caps the COMBINED draw. Enforcement (see
599// serviceCurrentGovernor in nml_hand_exo.cpp) is two-sided:
600//
601// feed-forward Issuing a goal immediately clamps the fleet to the static
602// worst case, budget / sum(nominal of moving motors), so the
603// very first transient is bounded before anything is measured.
604// feedback Measured aggregate PRESENT_CURRENT then relaxes that clamp
605// back toward full per-motor effort whenever the real draw
606// leaves headroom -- so one working motor keeps full torque and
607// the clamp only bites when the fleet genuinely nears the cap.
608//
609// Sized for the supply, NOT for the motors. Default assumes roughly 1 A usable,
610// leaving headroom for the board, OLED and IMU. Raise it with
611// `set_total_current_lim:<mA>` once you know what your supply sustains; watch
612// `current_status` for the measured aggregate while you do.
